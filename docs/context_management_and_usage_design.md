# 上下文管理、Token 用量与缓存统计开发方案

更新：2026-09-24｜状态：E5.1 已接入，验收边界见 §15–16｜范围：Android / Flutter，延续现有 Dart AgentLoop

本文承接 E5，记录统一 Token 计量、请求事实、缓存统计、滚动摘要和单次长任务压缩的契约与实施范围。源码实现、本机可控验证、真实摘要质量和设备验收分开记录；本文不授权安装、清数据、数据库覆盖升级、提交或推送。

工程规则遵循 [AGENTS](../AGENTS.md)，UI 规则遵循 [DESIGN](../DESIGN.md)。当前产品契约见 [产品设计](./product_and_technical_design.md)，原有 E5 范围见 [扩展设计 §8](./agent_extensions_design.md#extensions-planning)，本方案建设顺序纳入 [实施计划](./implementation_plan.md)。

## 1. 目标与非目标

### 1.1 本次目标

1. 四协议提供统一、可解释的服务端用量，区分缺失、零值与不完整统计。
2. 显示当前分支下一请求的上下文预计占用、模型窗口和估算来源；输出预留仍参与预算。
3. 按请求、本次运行、整个会话统计输入、输出、缓存读取、缓存写入和推理明细。
4. 展示会话累计缓存命中率及请求用量明细，不重复计算缓存或推理 Token。
5. 在现有摘要基础上实现滚动更新，并支持一次用户任务内部的长工具循环压缩。
6. 压缩只改变模型活动窗口；历史、工具执行事实、产物和请求消耗仍可追溯。

### 1.2 不在本次范围

- 不接入计费账户、账单查询或价格目录；Token 消耗不等于实际扣费金额。
- 不引入精确 tokenizer 依赖，不承诺本地估算等于各模型的真实分词。
- 不建设向量检索、自动长期记忆、多代理调度或另一套 Agent 运行框架。
- 不接入 Codex 专用加密压缩状态，不自动选择其他摘要模型或切换协议。
- 不为了提高缓存命中率改写用户消息、降低推理等级或强制增加缓存控制字段。
- 不直接把 Pi / deepseek-harness 作为 Flutter 运行时依赖。

## 4. 三种数字必须分开

### 4.1 API 用量

服务端报告的一次请求输入、输出及缓存明细。累计用量来自多次实际请求，包含重复发送的历史，不用于判断当前窗口还剩多少容量。本地估算不得混入该累计值。

### 4.2 上下文预计占用

下一请求实际准备发送的系统提示、工具定义、消息和多模态内容占用。它对应当前分支、模型配置和压缩检查点，是预算与压缩的输入。

### 4.3 缓存命中率

服务端已报告的缓存读取量占同一统计范围输入总量的比例。缓存命中减少重复计算，不减少输入所占窗口。不得根据响应速度、文本相同、费用或本地重复率推测命中。

统一公式，`P` 为输入总量、`U` 为普通未缓存输入、`R` 为缓存读取、`Wc` 为缓存写入、`O` 为包含推理的输出：

```text
P = U + R + Wc                 # 仅在分桶完整且互斥时据此推导
T = P + O                     # 该协议口径能够完整覆盖输入与输出时
cacheHitRate = R / P           # P > 0，且分子分母都有效
sessionCacheHitRate = ΣR / ΣP  # 同一组请求，不能平均每个请求的百分比
```

示例：输入 10000，其中缓存读取 8000，输出 1000，则命中率为 80%、消耗为 11000；输入仍占 10000，不是 2000，也不是 18000。推理若是输出中的 600，则总量仍为 11000。

## 5. 统一用量契约

### 5.1 目标 TokenUsage

调整初版共享模型，不保留原型字段兼容包装。归一化用量只承载服务端报告或由同一报告可靠推导的数据；本地估算另存于 `ContextMeasurement`，移除二者共用 estimated 标记的设计。

| 字段 | 含义 |
|---|---|
| `promptTokens` | 输入总量，包含缓存读写；分桶不完整时仍可保留服务端输入总数 |
| `uncachedInputTokens` | 不包含缓存读写的普通输入；不能确定时为 null |
| `cacheReadTokens` | 服务端明确报告的缓存读取量 |
| `cacheWriteTokens` | 服务端明确报告的缓存创建/写入量 |
| `outputTokens` | 该协议归一化后的全部输出，包含已报告的推理部分 |
| `reasoningTokens` | outputTokens 的子集；不是额外相加项 |
| `totalTokens` | 完整请求总量；优先保留有效服务端总数，也可由完整 P、O 推导 |

所有计数字段可空，使用非负整数。总量字段与互斥分桶同时存在，是为了保留“总数已知、细分未提供”的常见响应，不建立多个可独立修改的计量来源。

字段级保留来源 `reported / derived` 与异常字段集合；完整性按所需指标计算，不用一个全局布尔值推断所有明细。来源信息随归一化结果保存，不保存原始响应正文。

### 5.2 缺失、零和矛盾

- 未返回、不支持、请求在 usage 到达前中断：null，不写成 0。
- 明确报告 0：保留 0；已知 P > 0 且 R = 0 才能显示命中率 0%。
- P = 0：命中率不适用，不显示 0% 或 100%。
- 只返回缓存数，没返回输入总量：不能把缓存数当作总输入。
- 总输入已知但缓存字段缺失：仍显示总输入；缓存率显示“未提供”。
- 分桶和总数矛盾、R > P、reasoning > output、负数或超出存储整数范围：保留能独立成立的指标，无效指标标不可用；不静默截成合法范围。
- 用量异常本身不把已经成功的正文改成聊天失败；以安全诊断代码记录字段问题，不输出原始响应或鉴权信息。

### 5.3 流式更新

同一请求的 usage 事件通常是累计快照，不能逐事件求和。适配器依据协议合并：只覆盖本事件明确出现的字段，保留此前已报告但本次省略的字段，最后完成快照用于收口；不以逐字段最大值掩盖服务端修订。终态后的迟到事件不更新记录。

某协议确实发送增量时，在该适配器内转换为累计快照，对上仍使用统一 `UsageChunk`。协议事实以脱敏样本和文档语义为依据，不猜测网关变体。

## 6. 四协议归一化

下表是实施时需由适配器落实并用脱敏样本覆盖的口径，不是让业务层根据模型名称选择公式。

| 协议 | 输入与缓存 | 输出与推理 | 总量与注意点 |
|---|---|---|---|
| OpenAI Chat Completions | `prompt_tokens` 为 P；`prompt_tokens_details.cached_tokens` 为 R；只有明确支持的缓存写字段才映射 Wc | `completion_tokens` 为 O；明细 reasoning 为其子集 | `total_tokens` 与 P + O 做一致性检查；DeepSeek 的明确字段在现有兼容适配职责内处理，不切协议 |
| OpenAI Responses | `input_tokens` 为 P；`input_tokens_details.cached_tokens` 为 R | `output_tokens` 为 O；`output_tokens_details.reasoning_tokens` 为子集 | 有效 `total_tokens` 或 P + O；加密 reasoning 内容不作为计费明细或公开思考 |
| Anthropic Messages | `input_tokens` 是普通输入；缓存读取、创建分别来自 `cache_read_input_tokens`、`cache_creation_input_tokens` | `output_tokens` 为 O；没有公开推理计数字段时 reasoning 为 null | P 需要普通输入与缓存分桶的完整口径；是否可将省略字段视为协议定义的零必须有依据，不能由业务层补零 |
| Google Generative AI | `promptTokenCount` 为 P；`cachedContentTokenCount` 为其中的缓存部分 | 以当前标准 usage 语义将 candidates 与 thoughts 归一化，避免漏计 thoughts 或重复相加 | 优先保留 `totalTokenCount`；已知分项不足以解释总量时，保留有效总数并标细分不完整，不把差额猜成推理 |

OpenAI/Google 的输入总量包含缓存；Anthropic 的 `input_tokens` 不等于包含缓存后的总输入。统一模型不得直接保存这些原字段再让页面自行拼公式。

对明确没有独立缓存写入分桶的协议，可以按已知协议关系计算未命中输入，但 `cacheWriteTokens` 展示仍需区分“未提供明细”和“明确为零”。跨网关有差异时增加有证据的适配规则，而不是添加通用正则猜测。

实现入口：`lib/providers/openai_completions/sse_decoder.dart`、`openai_responses/responses_decoder.dart`、`anthropic_messages/anthropic_decoder.dart`、`google_generative_ai/google_decoder.dart`。

## 7. 请求记录与统计事实来源

### 7.1 按真实尝试记录

新增初版 `ModelRequestRecord` / `model_requests`，作为 API 用量的唯一统计来源。它记录请求生命周期和计量，不复制消息正文，不另建会话或 Agent 事实库。

| 字段组 | 建议字段与职责 |
|---|---|
| 身份 | id、conversationId、runId、逻辑模型轮标识、attemptIndex；手动整理的 runId 可空 |
| 用途 | `chat / contextSummary / turnPrefixSummary`；摘要请求另关联 summaryJobId |
| 来源 | profileId、protocol、requestedModelId、服务端明确提供的 responseModelId；不按展示名猜来源 |
| 生命周期 | prepared、running、completed、failed、cancelled、interrupted；准备/开始/结束时间及安全错误分类 |
| 计量 | 归一化 usage、字段来源/有效性、样本修订号、是否完成收口 |
| 上下文基准 | 配置指纹、活动窗口代次、输入覆盖位置、输入估算与估算算法版本 |
| 关联 | 对应助手消息或摘要阶段；来源请求 ID 可空，不能依赖网关 ID 唯一 |
| 复制归属 | 可空 originRequestId，以及本会话是否实际发起该请求 |

主请求每次重试都是新记录，不覆盖上一尝试。`AgentRun.turnCount` 保持逻辑轮口径，`modelAttemptCount` 保持主聊天尝试口径；摘要调用通过用途分项计数，不混入工具轮数。

手动整理归属于会话级 summaryJob，保存独立配置快照，不伪造用户消息或 AgentRun。它与发送、恢复运行共用 ChatController 的操作互斥和取消入口；消耗计入会话的整理分项，不计入上一次已结束的运行。自动整理则明确归属于触发它的 runId。

### 7.2 持久化顺序与幂等

1. 构建并检查请求，在网络调用前保存 prepared 记录；未开始的准备不计为实际尝试。
2. 在正式调用/订阅 Provider 的边界计次并进入 running；此前重新检查取消。不以服务端是否接受请求来推断已知/未知用量。
3. 流式 usage 更新同一 requestId 的累计快照，节流落库；完成时强制提交最后样本。
4. 请求终态、助手消息或摘要阶段收口在同一仓储事务中关联；先完成已有异步写入，再发布终态。
5. 相同 requestId、相同修订的重复写入不增加累计；不同 requestId 即使数字完全相同也分别计数。
6. API 用量已到达但响应随后失败，仍保留已报告数字。完整消耗是否确定由报告完整性决定，不由 completed 状态单独决定。
7. 停止或进程退出前没拿到 usage：记录消耗未知，不能当作免费或零消耗。启动恢复把悬空请求收口为 interrupted，不重发请求。

网络和数据库没有跨系统事务，极端中断时无法保证补回服务端已消耗但未返回的数字。展示“已报告用量”，不宣称等于账单。

### 7.3 清除重复事实来源

目标 schema 中消息通过请求引用读取用量，摘要通过 summaryJobId 读取所属请求；运行汇总从请求记录计算。现有消息/运行/摘要 usage_json 不再作为可独立更新的计费副本，不实施双写过渡。领域对象可提供只读聚合结果，但不是另一份持久化权威值。

每个已执行请求最多关联一个主助手消息或一个摘要阶段。复用同一摘要不新建请求、不增加消耗。摘要被判定无收益或因分支变化不采用，只要请求已经发生，其用量仍计入。

服务商配置被删除或模型重命名，不删除历史请求计量；来源保存安全的身份快照，不能依赖现存配置才能展示，也不能通过 profile 外键级联清掉会话消耗。

复制会话时保留历史用量的来源标记供查看，但标为继承记录，不计入副本“本会话实际请求”；新请求正常累计。副本保存自包含的历史计量，来源 ID 不建立强制保留原会话的外键，删除原会话不破坏副本查看。复制不复制活动摘要检查点与 usage 基准。删除会话级联清理请求记录；活动运行的删除仍遵循现有停止与清理规则。

### 7.4 数据发布边界

当前初版 schema 为 8：新增请求表，移除消息/运行/摘要的重复 usage_json，摘要增加检查点元数据、可空 runId。2026-09-22 用户明确要求安装后，仅为已有 E5 安装加入 v7 → v8 例外：三处旧 usage 原始文本保存在 `usage_archives`，不解析旧口径、不伪造请求记录、不计入新统计；旧摘要和其他业务列原样保留。档案随会话复制、级联删除，不形成双写或其他版本升级链。假数据加密库验证重复打开、引用失败回滚和复制归属；设备备份与验证结果见实施计划。

## 8. 上下文计量服务

### 8.1 单一测量入口

在 `lib/features/chat/context/` 建立 `ContextMeter`，供请求预算和上下文 UI 共用。页面不自行遍历消息拼 Token，Provider 不依赖 UI。计量输入是实际将发送的内容投影，而不是气泡的显示文字。

`ContextMeasurement` 至少包含：

- conversationId、branchHeadId、contextGenerationId、配置指纹和内容修订。
- `estimatedInputTokens`、windowTokens、outputReserveTokens、marginTokens、可用输入预算。
- 来源 `usageAnchored / estimated / unavailable`，基准 requestId 和测量时间。
- system / tools / messages / images 的组成估算；组成之和不冒充实际 usage 总量。
- 活动摘要 ID、最近压缩前后估算、压缩状态与不能压缩的原因。

服务端记录保留“上次输入实际值”，测量保留“下次请求预计值”；即使以后同页展示，也不能共用一个无来源的 `tokens` 字段。

### 8.2 usage 基准与增量

以成功完成、输入计数有效的主聊天请求作为基准，持久化其当时输入估算和输入覆盖范围。摘要请求用量永远不能作为主聊天的上下文基准。

```text
P0 = 基准请求的服务端输入总量
E0 = 同一基准请求输入投影的本地估算
E1 = 当前下一请求输入投影的本地估算
nextInputEstimate = max(0, P0 + E1 - E0)
```

这里 E1 会包含后来被实际回放的助手正文、公开思考/必要协议状态、工具结果与用户增量，不再额外加一次基准请求的 outputTokens。这样不会把未回放的输出或推理 Token 全部机械塞回窗口。增量仍然是估算，值必须带约号。

仅在请求配置相同、基准对应的输入前缀未修改、内容增减能准确定位、估算算法版本一致时复用基准。模型/协议/端点、系统提示、工具定义、能力或影响请求形态的配置变化，以及编辑、切离分支、复制、压缩激活，均使基准失效。

上下文指纹拆为配置指纹与覆盖内容指纹：正常追加新内容不能因完整请求 hash 改变就误判基准失效。指纹只在业务存储内部使用，不记录含密钥的 header，不把完整提示词写入日志。

压缩后先用新窗口的整体估算，标记“压缩后估算”；收到新请求 usage 再建立基准。此版不跨压缩代次继续减旧锚点，以免删除旧原文后仍保留失真的服务端修正值。

### 8.3 估算与真实请求一致

- 测量系统提示、工具 schema、文本、回放的推理状态、工具参数/结果、图片和必要协议包络。
- 不支持图片的模型按实际发送的替代文本计量，不按 UI 中仍显示的图片计量。
- 已有历史截图淘汰、工具结果预览截断和附件文本抽取必须先形成请求投影，再测量。
- 签名与加密载荷只影响协议计量，不转成公开思考或用户可见文本。
- 初版保留现有 UTF-8 保守估算作为无基准回退，并标记版本；不要为了数字看起来接近 Pi 而直接改成字符数除以四。后续更换估算器需单独比较中文、代码、JSON 与多模态样本。
- 图片计量有明确协议/模型规则时由适配层提供；否则使用标明来源的保守预留，不承诺固定 4096 是所有图片的上界。
- 本地准入不能保证网关一定接受。模型窗口配置错误、图片/协议估算误差仍可能产生服务端超窗错误，由第 11 节收尾。

## 9. 预算与压缩触发

### 9.1 预算参数

设 W 为配置窗口，O 为协议实际输出上限或明确标注的本地预留，M 为协议余量，C 为可用输入预算：

```text
C = W - O - M
自动压缩阈值 = floor(C × 0.8)
压缩后目标   = floor(C × 0.6)
最近原文软预算 = min(20000, floor(C × 0.5))
```

80% 延续现有触发习惯；60% 与最近保留量为本方案的初版策略值，不是 Pi 的原样默认值，也不是吞吐或质量保证。策略集中在一个 `ContextPolicy`，与模型配置一起固定进运行快照；首版不增加一排面向用户的高级滑杆。

W 的解析顺序为用户手填 > models.dev 目录 > 本地默认 128000，M = 1024；窗口来源以三态声明：`用户配置窗口` / `models.dev 目录窗口` / `本地默认窗口`。目录值来自社区维护的 models.dev 快照，是服务商上限的参考值而非 API 实测，不保证准确性或及时性。O 必须结合适配器最终参数：例如当前 Anthropic 会使用自身默认 max_tokens，并可能因 thinking budget 抬高它，预算不能仍按 4096 计算。通过无副作用的请求规划结果共享有效参数，禁止控制器复制另一套协议公式。

其他协议未显式设置输出上限时，输出预留依次取 models.dev 目录输出上限、本地 4096，来源同样标为协议实参 / models.dev 目录 / 本地默认；服务端实际上限仍未知。目录输出上限位于协议实际参数与本地 4096 之间，只进预留，绝不下发为请求参数。不能为了预算方便悄悄给主请求增加 max_tokens、关闭推理或改温度。C <= 0 时明确报配置/预算错误，不发摘要尝试自救。

### 9.2 触发时机

- 第一轮模型请求前：完成当前分支与新输入装配后测量。
- 每组工具调用完成并落库后、下一模型请求前：重新测量，支持单次任务持续推进。
- 摘要激活、模型/助手切换或分支编辑后：使旧测量失效，按新配置重建。
- 手动“整理上下文”：仅空闲会话可用，复用同一机制；不自动发送下一轮聊天。
- 服务端明确返回 contextLimit：按第 11 节进行至多一次有变化的压缩恢复。

达到阈值但没有可压缩材料时，若仍在 C 内就继续；超过 C 且无法降低则保存明确失败。不为了达到占用百分比自动删除当前任务、拆工具组或改用户模型参数。

### 9.3 models.dev 模型目录机制

目录只承载 `limit.context`（上下文窗口）与 `limit.output`（输出上限）两项，保留所有服务商的有效条目，按模型 ID 跨服务商匹配，`custom`/`ollama` 同样生效。去除查询 ID 首尾空白后，精确 ID 优先于命名空间末段互配；同级优先已选预设，再按模型 ID、服务商 ID 排序，避免依赖目录返回顺序。未命中才回退本地默认；请求中的模型 ID、协议和地址保持不变。目录缓存格式版本 2 不复用此前仅含白名单服务商的版本 1 缓存与 ETag；先使用新版内置全量快照，下次手动刷新重新完整拉取，不迁移或改动用户配置。

内置快照 `assets/models_catalog.json` 随包发布，由 `tool/generate_models_catalog.dart` 从 models.dev `api.json` 精简生成。运行期仅由用户在 Providers 页手动刷新：带 ETag 增量拉取（200 全量 / 304 未变化），精简后经独立临时文件 + rename 原子写入应用私有目录的文件缓存；首次解析等待本地缓存初始化，有效缓存优先于内置快照，无效/缺失缓存回退内置快照，资产也不可用时走本地默认。无 TTL 自动拉取，零/负数/非有限上限视为缺失；空或错误的响应不覆盖有效缓存。缓存初始化失败立即回退，不由 provider 自动重试阻塞聊天；手动刷新可重试初始化。写入失败保留原目录；离开刷新页取消请求，迟到网络响应不发布，已开始的原子写完成后仍同步应用级目录。

窗口、窗口来源及候选目录输出上限在 `RunConfiguration` 创建时固定并持久化；每次计量仍优先采用适配器最终输出参数并记录预留来源。resume 与驱动层不重新读取目录，运行中途刷新目录不影响既有运行，空闲预览和新运行使用更新后的目录。models.dev 是社区维护的数据源，条目准确性与及时性不作保证，以服务商实际行为为准，用户手填值始终优先；编辑器的目录提示与校验不回写用户输入。部分条目的输出上限等于或大于上下文窗口，此时不偷偷裁小预留：明确显示窗口、预留和余量的配置错误，用户可手填输出上限修正。

实现入口：[目录模型](../lib/data/models/model_catalog.dart)、[文件缓存](../lib/data/datasources/local/model_catalog_cache.dart)、[刷新客户端](../lib/data/datasources/remote/models_dev_client.dart)、[Providers 页刷新入口](../lib/features/providers_config/providers_page.dart)。

## 10. Pi 式滚动压缩

### 10.1 历史与活动窗口分离

原始消息树、工具记录、文件和请求计量是事实来源；摘要只影响某个分支本次发送什么。目标窗口结构为：

```text
当前系统提示与开放工具定义
有来源的最新累计摘要
宿主保留的动作事实与必要引用
当前任务原文及最近完整交互（按原始顺序，不重复注入）
检查点之后的新增内容
```

这比现有“旧用户原文和所有工具组始终驻留”更宽。U4 落地时必须同步 AGENTS 第 9 节和扩展设计 §8.2，明确：原始完整工具组不删除；模型窗口中的闭合历史组可被有来源摘要整体覆盖；保留部分不得出现孤立调用/结果。未收口调用、当前任务、用户拒绝与外部动作事实仍受保护。不能只删除现有 protected 判断就认为完成对齐。

当前首版保守实现：只让宿主类型白名单内的成功只读组退出原文窗口。MCP、任意 shell、设备与其他外部动作、错误/拒绝、图片和未收口组继续完整保留；不尝试用摘要替代无法有界表达的动作事实。AGENTS 和扩展设计已同步这一边界。

### 10.2 切分单位

先将历史解析成完整交互组，再从尾部按预算选取保留区间：

- 普通用户/助手消息可以形成独立边界。
- 一条助手消息里的多个调用与所有对应结果视为一个工具组；不能在其中切开。
- 结果尚未落库、等待确认、executing、awaitingUser 的组不进入摘要。
- 中断后补齐的合成结果可组成闭合组，但错误与未知效果不能改写为成功。
- 工具 ID 配对按应用侧记录归属，不假设 Provider callId 跨轮全局唯一。
- 不要求至少三条用户消息；单次运行也可找到已闭合的历史工具组。

最近原文软预算不是允许丢弃超大最新组的硬上限。最后一个完整工具组、当前未结束组和当前任务原文需要整体保留；放不下就失败，不能截断调用参数后继续执行。

### 10.3 任务内切分

一次任务的前半段超过预算时：

```text
当前用户请求 + 已完成工具组 A/B/C/D/E/F
                          ↓
当前用户请求原文 + A/B/C 的任务进展摘要 + D/E/F 原文
```

任务前缀摘要包含原始任务引用、已做工作、尚未完成事项、继续理解尾部所需信息。当前用户请求仍原样回填，不能只依赖模型在摘要里复述它。

如果一次运行接纳了新的用户指令，当前有效的本轮用户指令组都受保护，不根据“继续”等关键词认定旧要求已被撤回。纯模型长输出并不自动创建新的用户轮次。

### 10.4 滚动更新与范围记录

第一次：旧历史 → 摘要 S1。后续：S1 + 新进入摘要范围的完整历史组 → 摘要 S2。禁止每次从会话起点重新发送所有已被 S1 覆盖的原文。

扩展现有 `ContextSummary`，作为可追溯检查点，而不是新增平行摘要系统：

| 字段 | 作用 |
|---|---|
| parentSummaryId | 上一有效摘要，形成累计来源链 |
| source / firstKept 位置 | 本次新增覆盖区间与第一个原文保留组；不依赖数组下标 |
| 覆盖 ID / 内容指纹 | 记录新增覆盖及摘要输入指纹；累计覆盖由父链求得 |
| sourceModel / algorithmVersion | 摘要来源与算法版本，不把来源模型变成权限 |
| sourceGeneration / resultingGeneration | 准备时与激活后的活动窗口代次 |
| summaryJobId | 关联本次所有摘要阶段和重试请求，独立计量 |
| summary 状态 | running / completed / failed / cancelled，表示生成状态 |
| 采用结果 | applied / noGain / tooLarge / stale，区分“完成”与“已采用” |
| 计量快照 | 压缩前后估算、目标预算和未采用原因，不能标成 API 实测压缩率 |

摘要可沿同一分支的后代继续使用，不要求新增用户消息后的覆盖区间与旧摘要完全相同。切分支时重新验证来源：共享且未修改的完整覆盖前缀可以复用；只要覆盖 ID 不在新分支、内容变更或父摘要失效，就不能复用。不得把另一分支上才发生的动作写进当前分支摘要。

重新打开会话按有效检查点和其后消息重建窗口。摘要链只提供派生上下文，不替代消息树；编辑、重新生成、复制与删除仍使用原有会话事实。

### 10.5 摘要内容与事实保护

模型摘要使用固定段落：目标、约束与偏好、已完成、进行中、阻塞、关键决策、下一步、关键来源。材料以历史数据输入，不放进系统权限规则；摘要请求不开放工具、不写长期记忆。

宿主另外保留以下事实，不能只交给自然语言摘要判断：

- 当前用户任务与当前批准计划的实际修订。
- 已派发外部动作的调用记录引用、明确状态、目标和已知效果；失败/取消不表示撤销。
- 用户拒绝、取消、超时、结果缺失，以及需要下一轮重新观察的原因。
- 继续工作必需的产物/附件 ID 与文件路径，来自实际记录而非模型生成。
- 正在进行的动作、确认或用户协作等待；不得把它们总结成“已完成”。

优先压缩可重读的旧文件内容、查询结果和重复解释。只有宿主明确识别的只读工具允许仅以摘要和来源替代完整旧结果；不明效果的 MCP、任意 shell 和设备动作按外部效果处理，不能相信工具自称只读。这些外部动作组整体退出原文窗口时，必须另外保留宿主生成的实际状态、目标、已知效果与来源，不能只留下模型摘要。无法形成足够且有界的事实表示时，保留完整组或明确超限，不靠截断事实列表强行通过预算。

旧用户讨论可进入累计摘要，但模型不能可靠证明所有历史约束都被无损保留。因此不宣称语义无损或无限续跑；不能让摘要扩大工具许可，当前显式限制由宿主策略继续执行。长期不再驻留的原文仍需可按来源读取。

### 10.6 历史细节按需读取

在 U4 真正让旧工具组退出窗口时，加入内置只读 `read_history`，与压缩同时交付，不提前建设通用检索平台。

- 输入：宿主提供的 `sourceId`、可空 cursor、可选 maxBytes；sourceId 对应消息或工具记录，不是文件路径，首次读取不传 cursor。
- 只读取当前会话、当前分支及有效摘要覆盖的来源，拒绝跨会话、兄弟分支和任意数据库查询。
- 首版一次最多 8 KiB UTF-8，元数据和续读提示也计入上限；优先在行边界切分，单行过长时在有效 UTF-8 字符边界切分，不能让下一页重复同一段。
- 结果带来源、角色/工具状态、分页标识和 nextCursor；cursor 绑定来源修订和读取位置，每次重新校验权限与范围，来源变化提示从头读取。调用/参数作为历史数据返回，不变成待派发 ToolCall。
- 参数不暴露通用存储路径，不返回密钥、签名或加密推理状态；图片使用已有受控附件引用。
- 支持工具的运行开始时即确定该工具范围，默认只读 allow、尊重显式 deny；不能在运行中因发生压缩突然扩大快照。Plan Mode 仅把这一确定只读工具纳入宿主白名单。
- 不支持工具或 read_history 被禁止时，压缩选择必须保留继续任务所需细节；不能发出不可读取的引用后假装信息仍可恢复。

文件内容仍优先使用现有 read_file 的 path 与分页语义，read_history 只负责会话事实，不替代文件工具。

### 10.7 摘要请求预算与分段

摘要的实际输入和输出同样走预算规划，但不递归触发另一次自动摘要。使用当前运行的模型、协议与推理选择；摘要输出请求值以 min(4096, 主请求输出预留) 为初版目标，实际有效值仍以适配器规划为准，不能忽略推理带来的最低输出要求。

输入包括上一摘要、选中的新增闭合组、来源标签和本次摘要指令。旧大结果可生成明确标注截断的摘要输入预览，但状态、错误、目标和必要产物引用单独保留；不能在半截 JSON 中截掉动作状态。原始结果不改写。

若选定材料放不进摘要请求，按完整组缩小本次覆盖区间、形成中间摘要候选，再继续处理剩余部分。中间候选可以作为下一阶段输入，但不提前激活为主聊天窗口；只有最终候选通过第 10.8 节检查才切换。中途取消或任一阶段失败，原活动窗口保持不变。每个摘要阶段有独立请求记录；同一次压缩工作首版最多 3 个阶段，每个阶段必须推进覆盖边界并降低待处理体积，不形成递归或无限摘要循环。

没有可容纳的首组、上一摘要自身过大、必要事实已占满窗口时明确停止。摘要暂态错误首版不自动重试，同一运行、同一来源指纹不重复收费尝试；用户后续新运行可以再试。以后如增加摘要重试，必须另列预算并逐尝试记录。

### 10.8 激活前检查

摘要完成只产生候选，随后检查：

1. 请求完整结束、正文非空、没有工具调用，未因输出上限截断。
2. 覆盖范围、父摘要、分支和来源指纹仍匹配；停止或旧结果不能激活。
3. 必要事实与最新完整组仍在，重建后的调用/结果配对有效。
4. 使用同一配置、同一算法版本的纯本地估算比较压缩前后，确认体积下降，不能把旧实际 usage 与新估算相减后称作实测收益。新窗口重新测量后，自动压缩应降到触发阈值以下，尽量达到 60% 目标。只变小但仍超阈值，最多在剩余阶段预算内扩大覆盖后继续整理。
5. 新窗口不超过 C；若摘要无收益，原窗口仍可容纳则继续原请求，否则明确失败。
6. 在事务中保存采用结果和 resultingGeneration；当前分支的活动代次从已采用检查点及其内容修订确定，不用跨分支的全局摘要指针。事务提交后才能发布新的预算与发送后续请求。

检查失败时保留已发生的摘要请求用量及生成材料供查看，但不替换活动窗口。取消/存储失败不继续主模型调用。

## 11. AgentLoop 接线、错误与取消

### 11.1 调用顺序

```text
当前分支与运行快照
  → 解析活动检查点、完整工具组、附件和协议回放状态
  → 形成真实请求投影与预算规划
  → ContextMeter 测量
  → 必要时 CompactionCoordinator 整理并激活检查点
  → 再测量并完成准入
  → 创建主请求记录，调用 AiProvider
  → usage / 正文 / 思考分别累积并收口
  → 工具按原策略执行并保存结果
  → 回到同一 AgentLoop 的下一模型轮
```

不新增第二套 AgentLoop，不把压缩放到页面 build，不让 Provider 调工具。Controller 只编排，预算、分组、摘要候选和统计计算拆到职责明确的模块。

### 11.2 普通重试与超窗恢复不同

普通暂态错误保留现有固定请求上下文重试规则，失败输出不拼入下次尝试；每次请求独立计量。

仅对协议明确分类的 contextLimit，允许每个逻辑轮一次“重新构建上下文”的恢复流程：保存失败尝试 → 寻找有实际收益的压缩 → 以原任务、原模型参数重新请求。不是普通退避重试，也不根据错误文本尝试改参数。

没有可压缩材料、相同窗口再次超限、压缩失败或恢复请求再次超限，均结束并保存可见原因。已派发工具仍留在事实记录，不因压缩重新执行；失败尝试里的未派发工具不被恢复流程派发。

### 11.3 停止与资源收尾

- 自动整理中的主请求、摘要、分段摘要和退避都使用根运行的取消信号；手动整理使用同一控制器持有的本次操作取消域。停止即时禁止新的阶段和工具调度。
- 摘要已有部分文本可保存为取消材料，但不能激活为有效检查点。
- 取消传到底层 Dio/SSE 连接；不能仅停止页面刷新或等待下一 chunk 才结束。
- usage、摘要和消息写入统一处理异步失败；应用状态落库失败按 StorageFailure 收尾。
- 重启恢复不自动补发摘要或聊天；已激活检查点可重建，running 候选标失败/中断。
- 文件/产物读取失败仍属于对应工具结果，不因为参与上下文而一律升级为存储故障。

## 12. 统计范围与缓存率

### 12.1 三层范围

| 范围 | 计算对象 | 不应混入 |
|---|---|---|
| 单次请求 | 一个 requestId 的最终已报告快照 | 同轮其他重试、摘要或工具返回里的任意数字 |
| 本次运行 | 当前 runId 的实际请求，主聊天与摘要分项 | 上一次用户发送、继承记录 |
| 整个会话 | 本会话所有实际请求，含其他历史分支、失败、取消及摘要 | 从原会话复制的历史消耗、全账户其他应用消耗 |

默认“本次运行”对应一次用户发送或重新生成，不把 AgentLoop 的单个工具轮叫作一轮用户对话。用户批准计划产生的执行运行独立统计，可通过计划关联查看，不能偷偷与计划运行相加。

历史压缩、切换分支、重新打开会话不改变已报告累计消耗。活动窗口有多少消息与会话累计请求有多少次是两个维度。

### 12.2 不完整累计

每个指标累计已知值，并同时返回：实际请求数、该指标有效请求数、未知请求数、是否包含进行中请求。UI 显示“已报告输入 12.3k，2 次请求未提供”，不能只显示 12.3k 暗示完整总量。

缓存率只使用同时具有有效 P 和 R 的同一组请求。覆盖全部已结算请求时显示完整累计命中率；否则在详情中标“已报告请求命中率”及覆盖数，主界面不显示一个貌似覆盖全会话的百分比。不能用部分请求的缓存读作分子、全部请求输入作分母。

总消耗优先累计各请求有效 totalTokens；总量缺失但 P、O 都完整且协议允许推导时可参与。已知分桶之和不能冒充缺失部分已为零。推理明细只加进自己的明细列，不再次计入总消耗。

### 12.3 更新和性能

- 从请求记录按稳定 ID 聚合，不每收到一个 SSE 字符就全表扫描。
- 请求快照更新使用“撤销旧贡献、加入新贡献”或对应 SQL 聚合，二者均以同一记录为事实来源；不能把每次快照当新请求。
- 会话/运行聚合通过仓储查询和 Riverpod 注解 provider 提供；索引覆盖 conversationId、runId、purpose、状态及时间。
- 初版不另建难以恢复的累计计数表；若以后增加物化缓存，应能从请求记录重建并验证一致。
- 运行时预览可使用内存中的最新 usage，但标记未收口；历史账目与重开后的统计以持久化记录为准。

## 13. UI 与交互目标

本节是 UI 契约，已接入范围见 §2、§15；视觉与通用交互以 DESIGN 为准，不复制其他产品的 TUI 或胶囊布局。

### 13.1 聊天输入区

- 输入框下方、权限模式右侧展示低强调圆形进度条，百分比按预计输入 / 总窗口计算；超过窗口时圆环封顶但百分比保留实际值。窄屏大字号可将模式与圆环同移到独立一行。
- 运行中绑定运行快照；空闲时按当前分支和已选择配置展示下一请求估算。切换会话、分支或模型先使旧值失效，不能短暂展示另一会话的值。
- 空白聊天页不创建会话、不落库统计。未测量显示“待估算”或不显示数字；不能显示假的 0%。
- 初版不把未发送草稿算入已持久化会话占用；真正发送前的准入必须包含新输入。详情明确“当前会话；不含未发送草稿”。
- 正文流式期间不逐 Token 播放计数动画，不因统计挤压发送/停止、附件、模型和推理入口。

### 13.2 上下文小面板

点击圆环向上展开 tooltip 风格面板，不跳转页面：

- 已占用上下文显示预计输入整数并带约号；总上下文显示窗口整数及用户配置 / models.dev 目录 / 本地默认来源。
- 缓存命中率按本会话实际请求的成对字段汇总，展示覆盖请求数 / 实际请求数；继承记录排除。读取中、读取失败、未提供与零分母不适用分别显示，部分覆盖或未收口明确标注。
- 仅面板打开时订阅缓存统计，不随正文增量扫描请求表；缓存率不影响圆环占用。
- 外部点击与返回只关闭浮层，草稿和焦点保持；换会话关闭，模型/分支重估期间不显示旧占用。浮层避让安全区与键盘，高度不足时内部滚动。
- 删除“计划与上下文”页面、路由和顶栏入口。计划编辑/批准保留在聊天计划卡；不在小面板提供手动整理、组成估算及摘要检查点列表。自动整理与底层预算、摘要记录契约不变。

### 13.3 消息与运行详情

消息操作区提供轻量“用量”入口，直接打开底部面板，不在每条工具卡下重复统计；先显示所属运行总量，可切换整个会话并展开各请求。自动重试保留各失败尝试，累计不会只统计最终成功回答。摘要请求不伪装为助手对话消息。

计数缩写可显示 k/M，展开显示整数。估算数字带约号和语义标签；圆环百分比由读屏与小面板标明预计占用。缓存率显示精度不能把不足 100% 四舍五入成“全部命中”；0 分母显示不适用，未知显示未提供，部分覆盖明确范围。

### 13.4 状态、返回与无障碍

面板区分加载、无请求、部分数据和读取失败；请求明细区分进行中、失败与已取消。摘要采用状态继续保存于记录，不将摘要完成等同于当前分支可复用。

入口触区至少 48dp；320/360dp、横屏、2x 字号和键盘下可换行或滚动，不压缩字号。读屏读出“预计”“本地默认窗口”“部分请求未提供”，不只朗读百分比。保持 MaterialPage、预测返回、展开状态与滚动位置。

| 只报告缓存数、零输入、矛盾总量 | 不伪造总输入或命中率，不阻断有效正文 |
| 先失败后成功、部分输出后重试 | 两次实际请求分别累计；主请求重试上下文不包含失败输出 |
| usage 到达后失败、usage 前停止 | 已知用量保留；未知请求不当免费；无新请求派发 |
| 摘要成功但无收益、来源过期 | 消耗仍累计，活动窗口不替换 |
| 最近实际输入 + 新工具结果 | 预计占用增长，累计消耗只在真正模型请求报告后更新 |
| 图片降级、历史截图淘汰、跨模型状态 | 计量针对真实回放投影，未回放内容不计入增量 |
| Anthropic 高推理或默认输出 | 实际有效输出参数参与预算；不能只减本地 4096 |
| 连续至少三次压缩 | 只发送上次摘要与新增覆盖，不重复发送起点全部原文 |
| 只有一条用户消息的长工具任务 | 可在完整闭合组边界压缩并继续，无需伪造用户消息 |
| 一条助手消息多个调用 | 保留区间无孤立调用/结果，未收口组不进入摘要 |
| 用户拒绝、取消、外部效果不明 | 摘要不能转成成功；宿主事实和后续恢复规则仍在 |
| 大用户文档、大工具组、摘要自身超窗 | 不静默裁剪受保护事实；分段有上限，无进展明确停止 |
| contextLimit 恢复 | 每逻辑轮最多一次，后续失败明确收尾，已派发工具不重放 |
| 分支编辑/重新生成/切模型 | 摘要和计量各按自己的来源条件失效，不引用另一分支事实 |
| 复制/删除/重开 | 复制消耗标继承；新请求正常计量；删除级联正确；重开统计一致 |
| read_history 越界与分页 | 跨会话/分支拒绝；来源可追溯；8 KiB 包含元数据与续读信息 |
| 摘要等待响应、空闲 SSE 中停止 | 真实本地 HTTP 连接断开，不发后续主请求；假流不能代替 |
| usage/检查点落库失败 | StorageFailure 收尾，无“显示已采用但数据库未提交” |
| 会话含未报告请求 | 总量与缓存率标覆盖范围；加权公式正确，不平均百分比 |
| 窄屏、大字、横屏、返回、读屏 | 统计不挤压发送/停止，估算与未知有可听语义 |

优先扩展现有 `test/features/chat/context/`、`test/features/chat/context_transform_test.dart`、`test/features/tools/`、`test/providers/` 和 `test/ui/`。新增请求仓储与统计用例使用内存数据库、假凭据和可控网络，不读取手机配置或调用付费模型。

实现阶段按 AGENTS 执行 Dart 格式、分析、Flutter 测试和 diff 检查；只有生成输入变化才运行 build_runner，只有依赖变化才 pub get。纯 Dart/文档工作不触发原生桥接生成或 JVM 检查；若后续实际修改原生代码，再执行其对应检查。

真实摘要质量另用有目标、约束、外部动作和产物的脱敏长任务评估：检查任务延续、事实错误、重复动作建议与关键来源可找回。不把固定摘要测试通过等同于真实模型不会遗忘。

## 17. 风险与最终完成定义

- 精确服务端用量不等于精确下一请求占用；增量估算、多模态和协议差异仍存在。
- 缺失或中断请求的消耗不能由客户端可靠补回；统计必须标已报告范围。
- 自然语言摘要是有损的，多次滚动可能积累错误；原文、来源和宿主事实保护不能省略。
- 外部动作事实、当前任务或单个完整组本身可能超过窗口；本方案不承诺任意任务无限续跑。
- 请求表是应用状态，不能因“只是统计”吞掉写入失败；也不能为统计收集原始密钥或网络正文。
- 历史引用只提供读取，不授予工具许可，不让被摘要的第三方指令升级优先级。

完成本批意味着：统一用量可追溯、统计范围真实、上下文测量进入请求主链、滚动压缩可在单次长任务中工作，并且取消、失败、来源失效和存储故障都有明确收尾。成本金额、任意长任务保证、所有真实服务商支持和正式发行不包含在这一定义中。
